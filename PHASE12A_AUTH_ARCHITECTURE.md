# Phase 12A — Authentication architecture

Decision date: 4 October 2026. **Supabase Auth selected; activation disabled.** This is preparation for a private beta, not a launched account system. Phase 12B requires separate authorization. No provider dashboard settings, users, emails, migrations or learner ownership were changed.

## Existing identities and readiness
Phase 11H is CONDITIONAL PASS, with no blocking Critical/High finding within its tested scope. Original iPhone PWA restoration remains unverified; physical accessibility/browser coverage and comprehensive desktop design remain separately outstanding.

| Identifier | Current meaning | What it does not establish |
| --- | --- | --- |
| Shared staging access code | Entry to the private deployment | A person's identity or ownership of any existing learner |
| Signed `tutor_staging` cookie owner UUID | Browser session's ownership in `staging_resources` | Registered account identity or transferable recovery credential |
| Learner UUID | Stable record in `learner_state`, with associated placement/preferences/history | Permission to retrieve that record |
| Local-storage learner/session UUID | Browser selection hint | Authentication; another owner is rejected server-side |
| Future Supabase `auth.users.id` | Provider-verified account UUID | Beta membership or permission to a learner until an explicit association exists |
| Future application session | One independently revocable browser sign-in | A learner or a shared staging identity |

Current HMAC credentials expire server-side. Re-entering the access code with an authentic existing cookie, including an expired signed identity, renews that owner; clearing or losing the cookie yields a new owner. The one-year cookie retention is not one-year authorization. Resource ownership is enforced for learner and nested assessment/session/conversation/JLPT/review records. Existing private PostgreSQL schema is `tutor_private`; SQLite is the isolated development/test alternative. Neither browser context nor an email-match should merge identities.

## Provider and verification
Supabase Auth fits existing Supabase PostgreSQL and FastAPI: passwords, email verification/reset and provider refresh tokens remain Supabase's responsibility. No local password table, custom password hashing or browser Supabase SDK is proposed. The existing HTTPX dependency suffices for the small inactive verifier; use official Auth HTTP endpoints, not a home-grown signature algorithm.

`app/auth.py` calls the configured project's `/auth/v1/user` over TLS with a publishable API key and the supplied user token. Supabase performs signature verification. Local parsing is only an eligibility filter, never authentication: exact configured issuer, `authenticated` audience/role, non-anonymous account, canonical UUID subject/session, integer expiry/issued-at and optional not-before, permitted HS256/ES256/RS256 JWT type. Require provider success, matching user ID, verified email and recheck expiry after the request. No returned email/metadata is used as an ownership claim. [Supabase JWT verification](https://supabase.com/docs/guides/auth/jwts).

Verification is online and stateless: one request, five-second default total deadline, no redirect following/retry, bounded token/body, generic 401 or 503, no credential/body logging or success cache. The destination is trusted configuration, never token `iss`, `jku` or browser input. Hosted configuration accepts only Supabase HTTPS project origins; development can explicitly use HTTP loopback. The current utility accepts modern publishable keys only; legacy anon-JWT/custom-domain integration would need separate reviewed support. No service-role key or shared JWT signing secret is required. A caller must own a dedicated client lifecycle, without shared mutable account state.

Remote verification adds latency and provider availability dependency. It supports existing legacy signing without exporting a signing secret. Consider a maintained JWKS verifier only after confirming project signing mode and defining rotation/revocation behavior; do not introduce a competing session design. Mocked tests validate this boundary; real project configuration/signing has not been exercised.

## Selected future session approach — backend for frontend
This is our design proposal, not Supabase's JavaScript SSR cookie adapter. Vanilla JavaScript calls same-origin FastAPI APIs; it does not call Supabase or read/refresh tokens. FastAPI performs provider sign-in, verification and refresh and keeps access/refresh tokens in private server-side session storage. The browser receives only a cryptographically random opaque `__Host-goigrow_session` cookie, with Secure, HttpOnly, Path=/ and no Domain. SameSite=Lax is proposed for email-link navigation, with exact Origin/Fetch-Metadata checks and a session-bound CSRF token for every unsafe action, including login/logout; never depend on SameSite alone. Preserve current staging cookie and CSRF protections untouched until that transition is implemented. [OWASP session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

Proposed server record: hash of random session handle; verified account UUID; provider session UUID; encrypted provider tokens; encryption key version; created/last-use/absolute-expiry/revoked times. Encryption key lives only in deployment secrets, separate from staging and provider credentials. Use a maintained authenticated-encryption library in Phase 12B, not custom crypto. Rotate the handle at sign-in, recovery and privilege change; persist refresh rotation transactionally with a per-session lock so parallel tabs cannot reuse stale refresh tokens. Do not accept handles in URLs or JSON account IDs. No Supabase session tokens in localStorage, sessionStorage, public HTML, logs or worker caches.

Proposed application limits for owner review: 7-day absolute lifetime, 24-hour idle timeout, provider's default 1-hour JWT lifetime; expired sessions require independent sign-in. Application lookup/revocation runs on each protected request; provider verification is required before issuing/updating the account context. Supabase access JWTs can remain valid until expiry after logout: local logout must immediately revoke the application session and clear its cookie, as well as request provider-local logout. Global logout/reset/deletion must revoke all application sessions and check provider session existence/refresh eligibility; `/user` success alone is not proof of immediate global logout. Design the exact `auth.sessions` read permission and outage policy before activation. [Supabase sessions](https://supabase.com/docs/guides/auth/sessions), [sign-out scopes](https://supabase.com/docs/guides/auth/signout).

## Proposed additive schema and safe linking — not executed
Default: one account to one learner for the initial beta, with nullable/unlinked legacy profiles. Do not add an `account_id` value to every historical learner or backfill from browser/email/access code.

| Proposed structure | Constraints and purpose | Implementation phase |
| --- | --- | --- |
| `account_learner_links` | Account UUID primary key; learner UUID UNIQUE and FK to `learner_state`; verified link proof reference and timestamp | 12C |
| `account_sessions` | Unique session-handle hash, account/provider-session IDs, encrypted tokens and expiry/revocation fields | 12B |
| `beta_memberships` / invitation evidence | Explicit verified-account membership; hashed single-use invitation proof, expiry/revocation, atomic redemption | Invitation implementation in 12B/12E |
| Minimal security events | Event category/time, approved pseudonymous identifiers; no tokens/passwords/raw email | 12B onward |

PostgreSQL account UUID should reference `auth.users(id)` with deletion RESTRICT rather than a cascade into learner data; new application tables stay in `tutor_private`, revoked from PUBLIC/anon/authenticated database roles. SQLite equivalents use TEXT UUIDs and a fake provider account registry solely for isolated tests; do not copy credential tables. The existing SQL adapter does not translate arbitrary cross-schema Auth DDL, so use reviewed backend-specific migrations, rather than assuming SQLite SQL will work unchanged. Store provider account UUID, not email, as the stable key. No browser Data API access to these tables; existing privileged DATABASE_URL remains backend-only. Database-role permissions must be inspected before enabling the account authorizer.

Phase 12C link proof: a verified invited account plus fresh account authentication and authorization from the existing signed staging owner over the exact learner. Show the chosen profile and obtain explicit linking consent. Under one transaction/lock recheck both identities, current ownership and account/learner uniqueness; record the association/proof, leave learner IDs and child data intact. Ambiguous/multiple profiles or an already linked learner produce a conflict, never reassignment/merge. Lost original cookies require an owner-approved recovery process; a profile UUID, email match, shared code or copied token is insufficient.

After explicit linking, account ownership must take precedence for that learner and all descendants. Historical staging ownership may remain for audit, but cannot remain an alternative authorization path to linked records. Legacy unlinked learners keep the existing authorizer. Never use `account OR staging code` as a shortcut; resolve the resource's ownership mode first. Phase 12B sign-in alone must not claim old profiles or silently create replacements. New profile creation/linking is separately scoped and explicit.

Migration plan: back up and verify restoration using private operator storage; rehearse against disposable populated SQLite/PostgreSQL databases; add tables/indexes/FKs transactionally; test uniqueness, concurrent claims, rollback and unchanged record counts/IDs/history. No production migration is necessary for this phase. Code rollback disables new routes without destroying tables or reopening staging access to linked records. Once links exist, do not drop associations or deploy the old staging-only authorizer without an explicit restoration/access plan. Future account deletion first revokes sessions and follows an approved export/retention/deletion policy; provider deletion alone must not cascade into learning records. Owner must decide that policy before implementing deletion.

## Email, invitation and abuse controls
Keep provider Confirm Email enabled. Use provider reset/verification operations and exact approved callback routes, single-use short-lived state/PKCE or token-hash exchange appropriate to the official flow. Failed/expired links fail generically; recovery sessions are restricted to password update until completed. Never log email-link query tokens. Apply no-store, no-referrer and no third-party scripts to auth/callback pages. Destination after completion is a fixed same-origin route, never arbitrary `next`/redirect URLs. Planned production paths `/auth/callback` and `/auth/recovery` are proposals, not present routes. Configure their exact HTTPS URLs only during the reviewed implementation, with separate explicit localhost URLs for development. [Supabase password flows](https://supabase.com/docs/guides/auth/passwords), [redirect allowlists](https://supabase.com/docs/guides/auth/redirect-urls).

Initially disable public provider signups and use owner-controlled invitations/provisioning plus application beta membership. A hidden frontend button or backend flag alone cannot restrict direct provider signup. Before allowing invitation redemption, verify the chosen provider setting/hook prevents bypass and atomic membership redemption is enforced. Privileged invitation/deletion operations, if needed later, require a separate server-only admin client/key and owner approval; never substitute that key into the verifier.

Use generic login/reset/registration responses, provider and application limits for IP + normalized-email hash + global totals, bounded requests and limited retries. Apply timing/enumeration tests; do not disclose whether an account exists. Staging's current process-local limiter remains unchanged; durable enforcement is needed before multiple workers/public beta. Never log passwords, codes, auth headers, session cookies or raw provider errors. Security events need a retention/access policy. Enable provider abuse controls only after device/privacy review; no unsolicited CAPTCHA/OAuth integration here.

As of the decision date, Free includes 50,000 monthly active users, 500 MB database, 5 GB egress and may pause after a week of inactivity. Provider configurable idle/absolute session limits are Pro features; proposed application expiry must work on Free. Default SMTP currently delivers only to authorized team addresses, capped at two messages/hour, without delivery SLA. Custom SMTP is a necessary owner decision before outside testers; free-tier availability/deliverability must be verified, not assumed. No upgrade or email-provider account was created. [Supabase pricing](https://supabase.com/pricing), [SMTP restrictions](https://supabase.com/docs/guides/auth/auth-smtp).

## Environment and integration handover
Current additions (optional; do not set production values for this phase):

| Variable | Phase 12A behavior |
| --- | --- |
| `ACCOUNT_AUTH_ENABLED=false` | Default; true fails validation so partial auth cannot activate |
| `SUPABASE_AUTH_URL` | Blank by default; configured origin validated; never infer from private DATABASE_URL |
| `SUPABASE_AUTH_PUBLISHABLE_KEY` | Blank by default; SecretStr redaction; modern publishable key only; both origin/key required together |
| `SUPABASE_AUTH_TIMEOUT_SECONDS=5` | Total verification limit, bounded 1–10 seconds |

Existing Render/staging/AI/STT settings remain unchanged. Later encrypted-session storage requires a separate deployment key and reviewed migrations. No admin credential is requested now. Local offline tests use HTTPX MockTransport, fake accounts/tokens and isolated databases; optional CLI/local Supabase + email catcher may be evaluated for integration testing without connecting to production or sending external mail.

Phase 12B UI plan: small green/cream Sign in / invitation onboarding / Check email / Forgot password forms; Settings account/logout entry; clear session-expiry retry preserving unsent local text. Keep native labels/status/focus and Japanese input behavior. No framework. Callback processing stays server-side; frontend uses same-origin `me` results, never browser-supplied account IDs. Protected auth/API responses stay network-only and outside the existing three-resource worker allowlist; no account payload in offline fallback. `/me` must distinguish verified account, beta membership and linked/unlinked learner without leaking another user's record.

For Safari/iPhone PWA/other devices, each context independently signs in to the same account and obtains its own cookie. Phase 12C resolves the shared server-side account-to-learner link, validates owner scope and loads progress. Local stored IDs are hints only; stale foreign IDs never override the returned authorized learner. No cookie/localStorage sharing assumption or session-token copying. Today's original-profile restoration limitation is not solved by this preparation.

Existing project Auth signing/configuration, provider grants and redirect settings need verified inspection in the next authorized phase. These do not block disabled preparation, but block enabling a partially reviewed beta flow.

Phase 12B acceptance: implement persistent secure sessions, refresh concurrency/expiry/logout/CSRF, invitation enforcement, generic failures and email callbacks with mocked/local tests; verify no staging bypass or auto-link and no secret cache; rehearse deployment rollback; test provider project only with explicit permission for real emails/accounts. Phase 12C acceptance: separately approved transactional linking/recovery, account precedence for all nested records, legacy preservation, cross-context sign-in/profile restoration and conflict tests. **Stop after Phase 12A.**
